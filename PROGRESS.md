### ESCALATION 1: tornado-cli's proving key does not match the devnet's (original, Dec 2019) Tornado Verifier
Section / test: S2, T2.3 (blocks T2.3–T2.6)

What I expected (per BUILD-PLAN): tornado-cli's `build/circuits/withdraw.json` + `withdraw_proving_key.bin` with
websnark `genWitnessAndProve` produce proofs that the deployed Verifier `0xECD2…f01` accepts.

What happened:
- The deployed Verifier's 28 VK constants (PUSH32 operands of its bytecode) were compared with the VK points in the
  proving keys (decoded from websnark's Montgomery LE format; on-curve check passes):
  - tornado-cli `withdraw_proving_key.bin` (sha256 `8e2d2f22…a3af`) == tornado-core **v2.1** release (May 2020,
    post-trusted-setup-ceremony; alfa1.x `0x2dbfc3ec…e091`): **0 of its alfa1/beta2/delta2 values are in the deployed
    Verifier.** tornado-core's current `contracts/Verifier.sol`: 0/28 constants present.
  - tornado-core **v2.0** release (2019-12-17) `withdraw_proving_key.bin` (sha256 `95a7024d…a5c9`): alfa1, beta2,
    delta2 **all present**; its `withdraw_verification_key.json`: **28/28** constants present. This matches
    deployments/devnet.md ("replayed exactly as originally deployed (Dec 2019) — before a later governance-only
    verifier swap").
- Read-only experiments (local 1-leaf tree; `verifyProof` does not check roots against the pool, so no chain writes):
  1. tornado-cli key + websnark `4c0af6a8`: proof valid under the v2.1 VK off-chain (snarkjs `groth.isValid` → true),
     deployed Verifier `eth_call` → **false**. (Pipeline correct; wrong key for this chain.)
  2. v2.0 key + websnark `4c0af6a8` (tornado-cli's pin): invalid even under its own v2.0 VK (→ false). This is
     the "websnark produces wrong proofs" effect reported in deployments/devnet.md.
  3. v2.0 key + **websnark `peppersec/websnark#c254b596`** (the exact commit tornado-core v2.0 pinned in its
     package.json): valid under the v2.0 VK → true, and **deployed Verifier `eth_call verifyProof` → true**.

What I already ruled out: wrong decoding (on-curve check, VK json cross-check 28/28), wrong input ordering (same
code path verifies true in experiment 3), a broken pipeline (experiment 1 verifies under its own VK).

Options I see (do NOT pick one):
  A) Use tornado-core **v2.0 release** `withdraw.json` + `withdraw_proving_key.bin` (downloaded from the GitHub
     release, sha256-pinned) with websnark at **v2.0's own pin `c254b596`**; everything else stays tornado-cli's set
     (snarkjs `869181cf` — the same commit v2.0 pinned — circomlib `3b492f98`, fixed-merkle-tree 0.6.1). Same proving
     system and library (websnark WASM Groth16), no key conversion, still fully client-side. Verified working.
  B) As A, but also pin circomlib to v2.0's `34782260` (the complete v2.0 dependency set). Slightly more faithful;
     pedersen/MiMC are expected identical (T2.2 checks the MiMC tree against the chain either way).
  C) Pure-JS snarkjs prover with the v2.0 key converted from `.bin` (what the sidecar author did): needs key
     conversion and more work; no advantage now that A works.
  (Keeping tornado-cli's key as-is is impossible without replacing the pool's Verifier, which is forbidden.)
Impact on schedule: none if A or B (≈10 min to wire in); S2 is otherwise on track.
Waiting for owner decision.
